# Метрики в разработке для программистов, DevOps и SRE

## Что такое метрики в разработке?

**Метрики** — это количественные данные, которые измеряют различные аспекты процесса разработки, качества кода и работы приложения.

Проще говоря, это **цифры, которые превращают мнения "у нас всё хорошо" в объективные факты**. Они помогают:
- **Понимать** текущую ситуацию
- **Принимать решения** на основе данных, а не интуиции
- **Улучшать** процессы и продукт
- **Ставить цели** и отслеживать прогресс

## Метрики по командам

### 👨‍💻 Программисты (Software Developers)
**Фокус:** Качество кода, эффективность разработки и поддерживаемость кодовой базы

| Метрика | Что измеряет | Зачем нужна? |
|---------|--------------|--------------|
| **Coverage** (Покрытие кода тестами) | % кода, который выполняется при запуске тестов | Оценить защищенность кода от регрессий |
| **Cyclomatic Complexity** (Цикломатическая сложность) | Количество линейно независимых путей в коде | Обнаружить слишком сложные функции |
| **Количество технического долга** | Число "закладок" (TODO, FIXME) или тикетов на рефакторинг | Понять объем работы для поддержания чистоты кода |
| **Static Code Analysis Warnings** | Количество потенциальных багов и code style issues | Найти проблемы до запуска кода |
| **Lead Time for Changes** | Время от начала работы над кодом до его попадания в прод | Оценить скорость доставки фичи |

**Пример:** Программист видит, что цикломатическая сложность функции выросла до 15 (при норме 10). Это сигнал разбить её на несколько простых.

### 🔧 DevOps-инженеры
**Фокус:** Скорость, стабильность и эффективность процесса доставки кода (CI/CD)

| Метрика | Что измеряет | Зачем нужна? |
|---------|--------------|--------------|
| **Deployment Frequency** | Как часто команда выпускает изменения в продакшен | Показатель скорости разработки |
| **Lead Time for Changes** | Время от коммита до развертывания в проде | Показатель эффективности пайплайна |
| **Mean Time to Recovery (MTTR)** | Среднее время восстановления сервиса после сбоя | Показатель устойчивости |
| **Change Failure Rate** | % развертываний, приводящих к сбою в проде | Показатель стабильности |
| **CI Pipeline Duration** | Время выполнения пайплайна | Показатель эффективности инструментов |

**Пример:** DevOps видит, что `Lead Time` вырос с 10 минут до 2 часов. Пора искать "узкое место" в пайплайне.

### 🛡️ SRE (Site Reliability Engineers)
**Фокус:** Надежность, производительность и доступность сервиса **с точки зрения пользователя**

| Метрика | Что измеряет | Зачем нужна? |
|---------|--------------|--------------|
| **Availability** (Доступность) | % времени работы сервиса | Основа для **SLA** (договор с клиентом) |
| **SLI** (Service Level Indicator) | Конкретная метрика работы сервиса | Фактическое значение (например, "95-й перцентиль задержки = 200 мс") |
| **SLO** (Service Level Objective) | Целевое значение для SLI | Внутренняя цель для команды |
| **Error Budget** | Допустимое количество "простоев" | Главный инструмент управления риском |
| **Latency** (Задержка) | Время обработки запроса | Опыт самых "невезучих" пользователей (p95, p99) |
| **Traffic** (Нагрузка) | Запросов в секунду | Помогает планировать масштабирование |

**Пример:** SLO сервиса — 99.9% доступности. После сбоя доступность упала до 99.85%. **Error Budget** исчерпан — новые фичи блокируются до улучшения стабильности.

## Сводная таблица

| Команда | Ключевые метрики | Главный вопрос |
|---------|------------------|----------------|
| **Программисты** | Code Coverage, Cyclomatic Complexity | "Наш код качественный и удобный для поддержки?" |
| **DevOps** | Deployment Frequency, Lead Time, MTTR | "Мы доставляем код быстро и стабильно?" |
| **SRE** | Availability, SLO, Error Budget, Latency | "Пользователи довольны скоростью и надежностью сервиса?" |

Вместе эти метрики создают полную картину здоровья продукта: от качества отдельных строк кода до удовлетворенности конечного пользователя.
